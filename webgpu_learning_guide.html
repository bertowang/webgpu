1. 为什么学 WebGPU

WebGPU 是新一代 Web 图形与计算 API，提供对现代 GPU 的低开销访问。

它解决了 WebGL 的什么问题？

维度WebGLWebGPU
抽象层次全局状态机，驱动隐式管理显式对象，开发者掌控状态
CPU 开销每次调用都做验证，开销高命令预编码批量提交，开销低
多线程受限原生支持 Worker 中编码命令
计算着色器需扩展一等公民（compute pipeline）
着色器语言GLSLWGSL（类型安全、可静态验证）
心智模型：把 WebGPU 想象成一条工厂流水线。你先把原料（顶点数据）放进仓库（Buffer），设计好图纸（Pipeline），写好工人指令（WGSL），然后把订单（CommandBuffer）一次性交给调度中心（Queue）执行。

本指南的学习路径

概念→ API 对象→ WGSL→ 管线→ 一帧渲染→ 旋转立方体

2. 核心概念

理解这些对象，就理解了 WebGPU 的骨架。

2.1 设备层次：Adapter → Device → Queue

对象作用为什么需要它
GPUAdapter代表一块物理 GPU（或软件回退）先探测硬件能力（features / limits），再决定怎么用
GPUDevice逻辑设备，所有资源的工厂资源隔离域，不同 Device 间资源不共享
GPUQueue命令队列批量提交命令，保证顺序，CPU 不必阻塞等待

2.2 资源对象

资源类比关键点
GPUBuffer线性内存块创建时必须声明 usage（VERTEX/INDEX/UNIFORM…），之后不可改
GPUTexture二维/三维图像用于颜色附件、深度附件、采样贴图
GPUSampler采样规则定义纹理过滤与寻址方式

2.3 绑定模型：Layout → BindGroup

WGSL 里的 @group(0) @binding(0) 是"插槽号"，GPUBindGroup 负责把真实的 Buffer/Texture 填进这些插槽。

这层间接设计让同一个管线可以切换不同资源——只需传入不同的 BindGroup，不必重建管线。

2.4 管线（Pipeline）

GPURenderPipeline 把着色器、顶点格式、图元拓扑、深度状态固化为一个不可变对象。创建时做严格验证（成本高），渲染时几乎零开销，所以只创建一次、每帧复用。

3. 一帧的生命周期

从 JS 数据到屏幕像素，一帧经过 8 个节点。

1 准备源数据→2 创建 Buffer→3 编译 WGSL→4 BindGroup→5 RenderPipeline→6 编码命令→7 提交队列→8 呈现画布

4. 初始化设备与上下文

所有 WebGPU 程序的第一步：拿设备、配画布。

TypeScript
        // 1) 获取 WebGPU 入口；旧浏览器没有 navigator.gpu
        const gpuApi = (navigator as unknown as { gpu?: GpuLike }).gpu;
        if (!gpuApi) throw new Error('当前浏览器不支持 WebGPU');
        // 2) 请求适配器与设备；device 是创建所有 GPU 资源的入口
        const adapter = await gpuApi.requestAdapter();   // 适配器代表一块可用 GPU
        if (!adapter) throw new Error('未找到 WebGPU 适配器');
        this.device = await adapter.requestDevice();     // 后续 createBuffer / createPipeline 都从 device 出发

        // 3) 配置画布：设备 + 平台推荐格式
        this.resizeCanvas();
        // webgpu 上下文把 canvas 与 device 连接起来；类型断言是因为 lib.dom 未必声明 WebGPU
        const context = this.canvas.getContext('webgpu') as unknown as {
            configure(desc: unknown): void;
            getCurrentTexture(): TextureLike;
        };
        this.context = context;
        // 选平台偏好格式，避免额外的纹理格式转换
        const format = gpuApi.getPreferredCanvasFormat();
        this.context.configure({ device: this.device, format, alphaMode: 'opaque' }); // opaque 不保留 alpha，合成更快
gpuApi：从 navigator.gpu 读取，是 WebGPU 的入口对象。示例用 as unknown as { gpu?: GpuLike } 做类型断言，是因为 TypeScript 原生 DOM 类型不一定包含 WebGPU 定义；GpuLike 是示例自定义的最小接口，gpu? 表示浏览器可能不支持，所以下一行先判空。
getPreferredCanvasFormat()：返回平台偏好格式（通常 bgra8unorm），避免通道顺序转换开销。alphaMode:'opaque' 让合成阶段更快。

5. 渲染机制入门

一帧渲染可以拆成三件事：准备数据（缓冲区）、定义计算（WGSL）、装配流水线（渲染管线）。本章先建立这条主线，再按 5.2 / 5.3 / 5.4 的顺序逐个拆解。

5.1 全局视角：一帧渲染的数据流

最小骨架

完整 WGSL 里同时出现矩阵、结构体、插值，初学者容易一次接收太多。先只看这个最小骨架：它画一个红色三角形，没有任何矩阵和绑定。

WGSL
// 顶点着色器：只把位置原样输出，不做变换
@vertex
fn vs(@location(0) pos : vec3f) -> @builtin(position) vec4f { // @location(0) 对应 shaderLocation:0；@builtin(position) 必须输出
    // 输出裁剪空间坐标；这里假设 pos 已经在 NDC 附近
    return vec4f(pos, 1.0);
}

// 片段着色器：所有像素都涂成红色
@fragment
fn fs() -> @location(0) vec4f { // @location(0) 对应画布 colorAttachments[0]
    return vec4f(1.0, 0.0, 0.0, 1.0); // RGBA：红、完全不透明
}

读懂这两点后，再回到 5.3 节的完整版，你只需额外理解三件事：

  • 结构体 VertexOutput：把"位置 + 颜色"打包传递（因为片段阶段要用到顶点算出的颜色）。
  • 矩阵 uniforms.mvp * vec4f(position, 1.0)：把顶点从模型空间变换到裁剪空间（第 6 章讲）。
  • var<uniform>：一个所有顶点共享的只读全局变量（5.2 节讲怎么绑定）。

每节记住 3 件事

5.2 节 缓冲区
  1. 顶点缓冲：静态形状 + 颜色，mappedAtCreation 一次上传。
  2. 索引缓冲：复用顶点，减少数据量。
  3. Uniform 缓冲：每帧变化的矩阵，writeBuffer 更新。
5.3 节 WGSL
  1. @vertex 决定"顶点在哪"，必须输出 @builtin(position)。
  2. @fragment 决定"像素什么颜色"，返回 @location(0) 颜色。
  3. @location / @binding 是和 JS 对接的"编号"。
5.4 节 管线
  1. vertex.buffers 描述"数据怎么读"（stride / offset / format）。
  2. fragment.targets 描述"结果写到哪"（画布格式）。
  3. depthStencil 打开深度测试，解决遮挡。
把它们接起来
  1. 着色器里的编号 ↔ JS 里的 shaderLocation / binding。
  2. 编号对不上 = 编译报错或画面错位。
  3. 先跑通最小骨架，再逐项加功能。

5.2 缓冲区与绑定：把数据送进 GPU

把 JS 数据上传为 GPU 资源，并建立着色器可见的绑定。

阅读提示：本节会出现 @group(0) @binding(0) 和 getBindGroupLayout(0)。这里只需把它们理解为"WGSL 声明的输入编号"和"管线提供的绑定规则"；WGSL 的完整写法见 5.3 节，管线如何生成布局见 5.4 节。

TypeScript
        // 顶点缓冲：静态形状 + 颜色，每个顶点一份
        const vertexBuffer = this.device.createBuffer({
            size: vertexData.byteLength, // 字节数，不是元素个数
            usage: gpuGlobal.GPUBufferUsage.VERTEX | gpuGlobal.GPUBufferUsage.COPY_DST, // 顶点缓冲 + CPU 可写入
            mappedAtCreation: true // 创建时立即映射，适合一次性上传
        });
        new Float32Array(vertexBuffer.getMappedRange()).set(vertexData); // TypedArray 视图写入 position+color
        vertexBuffer.unmap(); // 解除映射后 GPU 才能读取

        // 索引缓冲：复用顶点，减少重复数据
        const indexBuffer = this.device.createBuffer({
            size: indices.byteLength, // 索引数据字节数
            usage: gpuGlobal.GPUBufferUsage.INDEX | gpuGlobal.GPUBufferUsage.COPY_DST, // 索引缓冲 + CPU 可写入
            mappedAtCreation: true // 一次性上传
        });
        new Uint16Array(indexBuffer.getMappedRange()).set(indices); // uint16 索引，与 drawIndexed 的类型一致
        indexBuffer.unmap(); // 解除映射

        // Uniform 缓冲：所有顶点共享的 MVP 矩阵，每帧更新
        this.uniformBuffer = this.device.createBuffer({
            size: 64, // mat4x4f = 16 个 f32 = 64 字节
            usage: gpuGlobal.GPUBufferUsage.UNIFORM | gpuGlobal.GPUBufferUsage.COPY_DST // 着色器只读 + writeBuffer 更新
        });
        // BindGroup 是"资源插槽表"：
        // - WGSL 的 @group(0) @binding(0) 声明一个 uniform 输入口
        // - layout 描述这个口的类型与可见阶段
        // - entries 把真实 buffer 填进这个口
        this.bindGroup = this.device.createBindGroup({
            layout: this.pipeline.getBindGroupLayout(0), // 复用管线自动推导的布局（类型/阶段约束）
            entries: [{ binding: 0, resource: { buffer: this.uniformBuffer } }] // 0 号插槽 ← uniformBuffer
        }); // 绘制时通过 pass.setBindGroup(0, ...) 启用这组绑定

顶点缓冲（上面代码中的 vertexBuffer）：存放静态的"形状 + 颜色"数据，每个顶点一份；usage 标记为 VERTEX，通过 mappedAtCreation 一次性写入。

Uniform 缓冲（上面代码中的 uniformBuffer）：存放所有顶点共享的参数，本例是 MVP 矩阵；它通过 bindGroup 绑定给着色器，而不是放进顶点缓冲。

createBindGroup() 的参数详解

整体结构：this.device 是 GPUDevice 实例，也是创建 buffer / texture / pipeline / bindGroup 的工厂；createBindGroup(descriptor) 接收一个描述对象，返回 GPUBindGroup。这里把结果存入 this.bindGroup，后续绘制时通过 pass.setBindGroup(0, this.bindGroup) 使用。

字段作用本例值
layout绑定组的类型契约：声明每个 binding 编号允许什么资源、在哪个着色阶段可见、buffer 是 uniform 还是 storage。getBindGroupLayout(0) 从管线取出第 0 组布局，对应 WGSL @group(0)。因为管线用了 layout: 'auto'，布局已由管线自动生成；直接取回可保证与管线期望完全一致，省去手动 createBindGroupLayout()，也不会出现"布局对不上"。this.pipeline.getBindGroupLayout(0)（管线创建见 5.4 节）
entries资源填充列表：把真实 GPU 资源填进 layout 声明的插槽。数组每一项对应一个 WGSL @binding(n)。只有一项，因为 shader 只声明了 @binding(0)
entries[0].binding插槽编号，对应 WGSL @binding(0)；这个编号必须已在 layout 中声明。0
entries[0].resource放入插槽的真实资源。buffer 必须写成 { buffer: ... }，因为 GPUBindingResource 是联合类型，需要用它区分 sampler / textureView；直接写 this.uniformBuffer 会校验失败。纹理与采样器分别写作 textureView / sampler。{ buffer: this.uniformBuffer }
label（可选）调试用名称，会出现在验证错误信息中，不影响运行。本例未传
创建 BindGroup 时不传数据本身，只描述"哪个资源放到哪个插槽"。后续每帧用 writeBuffer() 修改 uniformBuffer 的内容，已经绑定好的 BindGroup 会自动看到新值，无需重建。
严格对齐：@group(0) ↔ getBindGroupLayout(0)，@binding(0) ↔ entries[0].binding，var<uniform> ↔ resource: { buffer }；三者必须一致，否则 setBindGroup 时校验失败。

BindGroup（上面代码中的 bindGroup）：它是 JS 与 WGSL 之间的"资源接线板"，把真实 buffer 接到着色器声明的插槽上。完整链路如下：

  1. WGSL 用 @group(0) @binding(0) 声明需要第 0 组里的 0 号插槽。
  2. 管线通过 layout 规定这个插槽的类型（uniform）与可见阶段（vertex）。
  3. BindGroup 用 entries 把 uniformBuffer 插入该插槽。
  4. 绘制时 pass.setBindGroup(0, this.bindGroup) 把整块接线板交给 GPU。

结果：着色器里的 uniforms.mvp 读到的就是 writeBuffer() 写入的矩阵。BindGroup 只需创建一次，每帧只更新 buffer 内容即可。

常见坑：mappedAtCreation: true 只适合一次性上传静态数据；每帧变化的 MVP 矩阵用 queue.writeBuffer() 更新同一个 Buffer，不要每帧重建。

5.3 WGSL：顶点与片段的计算

WGSL 是 WebGPU 的着色器语言，类型安全、可静态验证。

本节的 uniforms.mvp 读取的是 5.2 节创建的 uniformBuffer；@location 最终由 5.4 节的 attributes 落地。这里先关注着色器"怎么算"，接线细节已在 5.1 的对照表中出现。

顶点着色器 vs 片段着色器

阶段输入输出职责
@vertex顶点属性、Uniform@builtin(position) 裁剪空间坐标把顶点放到屏幕正确位置
@fragment插值后的顶点输出@location(0) 颜色决定每个像素的颜色

本例 WGSL 代码

WGSL
            code: `
                // 所有顶点共享的 Uniform：MVP 矩阵
                struct Uniforms { mvp: mat4x4f }; // 内存布局与 JS 写入的 64 字节矩阵一致
                @group(0) @binding(0) var<uniform> uniforms: Uniforms; // group/binding 编号必须与 JS bindGroup 一致
                // 顶点着色器输出：位置 + 颜色，交给光栅化和片段阶段
                struct VertexOutput {
                    @builtin(position) position : vec4f, // 裁剪空间坐标，顶点阶段必须输出
                    @location(0) color : vec4f // 插值后传给片段阶段；JS 侧是 shaderLocation:1
                };
                @vertex
                fn vertex_main(@location(0) position : vec3f, @location(1) color : vec3f) -> VertexOutput { // 两个属性分别来自顶点缓冲的 offset 0 / 12
                    var out: VertexOutput;
                    // 模型空间 → 裁剪空间
                    out.position = uniforms.mvp * vec4f(position, 1.0);
                    // 顶点颜色原样传给片段阶段
                    out.color = vec4f(color, 1.0);
                    return out;
                }
                @fragment
                fn fragment_main(input : VertexOutput) -> @location(0) vec4f { // 返回值写到画布颜色附件 0
                    // 输出到画布的 0 号颜色附件
                    return input.color;
                }
@location(0/1) 必须与 JS 侧 vertex.buffers.attributes 的 shaderLocation 一一对应；var<uniform> 是所有顶点共享的只读数据。

createRenderPipeline() 的参数详解

整体结构：this.device.createRenderPipeline(descriptor) 接收一个描述对象，返回一个不可变的 GPURenderPipeline。它把 WGSL 着色器、顶点数据格式、图元拓扑、深度状态一次性装配好；绘制时由 pass.setPipeline(this.pipeline) 启用。这里把结果存入 this.pipeline，后续 getBindGroupLayout(0) 与 setPipeline() 都会用到。

字段作用本例值
layout绑定布局。'auto' 让 WebGPU 根据 WGSL 中出现的 @group / @binding 自动生成布局；5.2 的 BindGroup 通过 getBindGroupLayout(0) 取回使用。'auto'
vertex顶点阶段配置：指定 WGSL module、顶点入口函数，以及顶点缓冲如何解读。{ module: shader, entryPoint: 'vertex_main', buffers: [...] }
vertex.buffers[]顶点缓冲布局数组。每项描述一个 GPUBuffer 的 arrayStride（每顶点字节数）和 attributes（属性列表）。本例只有一个顶点缓冲。[{ arrayStride: 24, attributes: [...] }]
attributes[]属性列表：每项用 shaderLocation 对应 WGSL @location，offset 给出顶点内字节偏移，format 给出数据类型。位置：location 0 / offset 0 / float32x3；颜色：location 1 / offset 12 / float32x3
fragment片段阶段配置：指定 WGSL module、片段入口函数与目标颜色附件。{ module: shader, entryPoint: 'fragment_main', targets: [{ format }] }
fragment.targets[]颜色目标数组：每个 target 对应一个片段输出 @location(n)，format 必须与画布配置一致。[{ format }]
primitive图元装配与光栅化状态：topology 决定顶点如何组成三角形，cullMode 决定是否剔除背面。{ topology: 'triangle-list', cullMode: 'none' }
depthStencil深度测试状态：format 是深度纹理格式，depthWriteEnabled 控制是否写入深度，depthCompare 决定通过条件。depth24plus / true / 'less'
label（可选）调试用名称，会出现在验证错误信息中，不影响运行。本例未传
与 BindGroup 的关系：管线创建时 layout: 'auto' 会根据 WGSL 生成布局；5.2 通过 pipeline.getBindGroupLayout(0) 取回第 0 组布局来创建 BindGroup。绘制时必须 setPipeline() 与 setBindGroup(0, ...) 配套使用，否则绑定与着色器期望不一致。

关键状态解析

配置项本例值为什么
arrayStride6 * 4 = 24每个顶点 6 个 float（position 3 + color 3）
offset: 0 / 12顶点内字节偏移 0 / 12位置占前 12 字节，颜色紧跟其后；真正对应 @location 的是 shaderLocation
topologytriangle-list每 3 个索引组成一个三角形
cullModenone教学示例不因顶点绕序丢失面
depthCompareless近处片段覆盖远处，正确表现遮挡

两组 0/1 分别是什么？

写法所在层含义本例
attributes[0] / attributes[1]JS 配置数组只是数组下标，表示"第 1 / 第 2 条属性描述"，不会传给着色器。两条属性描述
shaderLocation: 0 / 1WGSL 输入契约对应着色器的 @location(0) / @location(1)，必须与 WGSL 一致。位置 / 颜色
offset: 0 / 12顶点内部字节位置从每个顶点数据的第几个字节开始读。前 12 字节位置，后 12 字节颜色
buffers[0] / setVertexBuffer(0, ...)顶点缓冲槽位指定使用哪个 GPUBuffer。本例只有一个缓冲
一句话：attributes[i] 的 i 是"第几条配置"，shaderLocation 才是"着色器第几个输入口"。两者数值恰好都是 0 / 1，但含义不同；真正必须与 WGSL 对齐的是 shaderLocation。即使把颜色配置写到 attributes[0]，只要它标 shaderLocation: 1 且 offset 指向颜色数据，依然正确。

6. 3D 数学：MVP 矩阵

顶点从模型空间到屏幕，要依次经过 Model → View → Projection 变换。

模型空间×Model→ 世界空间×View→ 相机空间×Projection→ 裁剪空间

矩阵乘法在 TS 中写成 mat4Multiply(mat4Multiply(projection, view), model)，因为列主序下变换从右向左生效。

TypeScript
/** 矩阵乘法：a × b，列主序 */
function mat4Multiply(a: Mat4, b: Mat4): Mat4 {
    const out = new Float32Array(16);
    // 列主序：a[r + k*4] 是第 k 列第 r 行
    for (let c = 0; c < 4; c++) {
        for (let r = 0; r < 4; r++) {
            let sum = 0;
            for (let k = 0; k < 4; k++) sum += a[r + k * 4] * b[k + c * 4]; // 结果第 c 列第 r 行 = A 第 r 行点乘 B 第 c 列
            out[r + c * 4] = sum;
        }
    }
    return out;
}

/** 绕 X 轴旋转 */
function mat4RotationX(angle: number): Mat4 {
    const c = Math.cos(angle), s = Math.sin(angle);
    return new Float32Array([1,0,0,0, 0,c,-s,0, 0,s,c,0, 0,0,0,1]); // 绕 X 轴：y/z 平面旋转
}

/** 绕 Y 轴旋转 */
function mat4RotationY(angle: number): Mat4 {
    const c = Math.cos(angle), s = Math.sin(angle);
    return new Float32Array([c,0,s,0, 0,1,0,0, -s,0,c,0, 0,0,0,1]); // 绕 Y 轴：x/z 平面旋转
}

/** 透视投影：fovy 弧度、宽高比、近远平面 */
function mat4Perspective(fovy: number, aspect: number, near: number, far: number): Mat4 {
    // 列主序透视矩阵；-1 把 z 写入 w，供 GPU 做透视除法
    const f = 1 / Math.tan(fovy / 2);
    return new Float32Array([
        f / aspect, 0, 0, 0, // x 方向按宽高比缩放
        0, f, 0, 0, // y 方向按焦距缩放
        0, 0, (far + near) / (near - far), -1, // z 映射 + 透视除法标记 w=-z
        0, 0, (2 * far * near) / (near - far), 0 // 深度平移项
    ]);
}
WGSL 与 WebGPU 约定列主序矩阵：a[i + k*4] 表示第 k 列第 i 行。用 Float32Array 存储可与 WGSL 的 f32 直接对齐。

7.2 类结构与渲染循环

WebGPURenderer 用 private 成员封装 device / pipeline / buffer 等状态，构造函数接收配置对象与状态回调。每帧流程：

TypeScript
    /** 每帧：更新矩阵 → 编码命令 → 提交 */
    private render(): void {
        try {
            this.resizeCanvas(); // 尺寸变化会影响 aspect 与画布纹理
            this.ensureDepthTexture(); // 尺寸变化时重建深度纹理
            if (!this.depthTexture || !this.canvas.width || !this.canvas.height) {
                requestAnimationFrame(() => this.render());
                return;
            }
            // 1) 更新 MVP：模型旋转 + 相机 + 透视
            this.rotation += 0.01;
            const aspect = this.canvas.width / this.canvas.height;
            const projection = mat4Perspective(this.fovY, aspect, this.near, this.far); // 投影：决定视野
            const view = mat4LookAt([0,0,3], [0,0,0], [0,1,0]); // 相机：眼睛在 (0,0,3) 看原点
            const model = mat4Multiply(mat4RotationY(this.rotation), mat4RotationX(this.rotation * 0.6)); // 模型：绕 Y/X 轴旋转
            const mvp = mat4Multiply(mat4Multiply(projection, view), model); // 组合顺序：投影 × 视图 × 模型
            // 2) 把新矩阵写入 Uniform 缓冲
            this.device.queue.writeBuffer(this.uniformBuffer, 0, mvp);

            // 3) 编码一帧：颜色附件 + 深度附件
            const encoder = this.device.createCommandEncoder();
            const pass = encoder.beginRenderPass({
                colorAttachments: [{ // 颜色目标：画布当前纹理
                    view: this.context.getCurrentTexture().createView(), // 本帧画布纹理的视图
                    clearValue: { r: 0.05, g: 0.06, b: 0.09, a: 1 }, // 深灰背景
                    loadOp: 'clear', // 不读取旧内容，直接清空
                    storeOp: 'store' // 绘制结果写回纹理
                }],
                depthStencilAttachment: {
                    view: this.depthTexture.createView(),
                    depthClearValue: 1.0, // 最远深度
                    depthLoadOp: 'clear', // 每帧清空深度缓冲
                    depthStoreOp: 'store' // 保留本帧深度用于遮挡判断
                }
            });
            // 4) 绑定资源并绘制：管线 + Uniform + 顶点/索引缓冲
            pass.setPipeline(this.pipeline);
            pass.setBindGroup(0, this.bindGroup);
            pass.setVertexBuffer(0, this.vertexBuffer);
            pass.setIndexBuffer(this.indexBuffer, 'uint16');
            pass.drawIndexed(this.indexCount);
            pass.end();
            // 5) 提交命令，GPU 异步执行
            this.device.queue.submit([encoder.finish()]);

            if (this.firstFrame.value) {
                this.firstFrame.value = false;
                this.onStatus('运行中：旋转立方体'); // 只上报一次，避免刷屏
            }
            requestAnimationFrame(() => this.render());
        } catch (error) {
            this.onStatus('渲染错误：' + (error as Error).message);
        }
    }

8.3 WGSL Compute Kernel

每个线程计算输出矩阵的一个元素；@builtin(global_invocation_id) 给出线程在网格中的坐标。

WGSL
// A、B 是只读输入，C 是可写输出
@group(0) @binding(0) var<storage, read> matrixA: array<f32>; // 输入矩阵 A，只读
@group(0) @binding(1) var<storage, read> matrixB: array<f32>; // 输入矩阵 B，只读
@group(0) @binding(2) var<storage, read_write> matrixC: array<f32>; // 输出矩阵 C，可写

// 一个 workgroup 只有 1 个线程；dispatch(4,4,1) 启动 16 个线程
@compute @workgroup_size(1)
fn main(@builtin(global_invocation_id) gid: vec3u) {
    // 每个线程负责输出矩阵的一个元素 (row, col)
    let row = gid.x; // 行号来自线程网格 x
    let col = gid.y; // 列号来自线程网格 y
    var sum = 0.0;
    // 点积：A 的第 row 行 × B 的第 col 列
    for (var k = 0u; k < 4u; k = k + 1u) {
        sum = sum + matrixA[row * 4u + k] * matrixB[k * 4u + col]; // 线性索引：row*4+k 与 k*4+col
    }
    matrixC[row * 4u + col] = sum; // 写回第 row 行第 col 列
}
@workgroup_size(1) 表示一个 workgroup 含 1 个线程；dispatchWorkgroups(4, 4, 1) 启动 4×4=16 个线程，正好覆盖 4×4 输出的每个元素。

8.6 从示例到真实 AI 模型

本例只是 4×4 矩阵乘法。真实模型（如 MobileNet、Llama）会做三点升级：

  • 分块（tiling）：用 workgroup 共享内存缓存矩阵块，减少全局内存访问。
  • 量化：把 f32 权重转成 f16 或 int8，降低显存占用与带宽压力。
  • 算子融合：把矩阵乘 + 激活函数写进同一个 kernel，避免中间结果写回内存。
现成方案：tfjs-backend-webgpu、ONNX Runtime Web、WebLLM 都基于上述原理，可直接在浏览器跑 CNN 与小型 LLM 推理。

9.4 实战：Softmax（Attention 的核心算子）

Softmax 需要处理一行数据：找最大值 → 求 exp 之和 → 归一化。直接对大数做 exp 会溢出，标准做法是先减最大值（数值稳定技巧）。

WGSL
@compute @workgroup_size(1)
fn main(@builtin(global_invocation_id) gid: vec3u) {
    let row = gid.x;                    // 每个线程负责一行
    var maxVal = input[row * N]; // 从第一个元素开始找最大值
    for (var i = 1u; i < N; i = i + 1u) {
        maxVal = max(maxVal, input[row * N + i]); // 数值稳定第一步：找到行最大值
    }
    // 第二遍：求 exp 之和
    var sum = 0.0;
    for (var i = 0u; i < N; i = i + 1u) {
        sum = sum + exp(input[row * N + i] - maxVal); // 减 max 防止 exp 溢出
    }
    // 第三遍：归一化并写回
    for (var i = 0u; i < N; i = i + 1u) {
        output[row * N + i] = exp(input[row * N + i] - maxVal) / sum; // 归一化后写回输出
    }
}

14. 设计哲学：WebGPU 与 OpenGL / Metal / Vulkan

WebGPU 更接近 Metal / Vulkan 的显式对象模型，但用"浏览器安全 + 强制验证 + 简化同步"换掉了裸机控制。下面从设计哲学和工程细节逐项对比。

14.1 一句话定位

API定位一句话理解
OpenGL跨平台、兼容旧的全局状态机图形 API"改全局状态，然后 draw"——驱动替你做很多隐式工作。
MetalApple 平台的低开销显式图形 / 计算 API对象化、命令缓冲、管线状态对象；与 macOS / iOS 深度绑定。
VulkanKhronos 的跨平台低开销显式 API把内存、同步、多线程编排全部交给应用，控制力最强也最繁琐。
WebGPU面向浏览器的显式、安全、可验证 API取 Metal / Vulkan 的对象化模型，去掉裸机复杂度，并保证浏览器不被 GPU 代码搞崩。
直觉：WebGPU 不是"WebGL 2.0"，而是"浏览器版的 Metal / Vulkan 精简模型"。它放弃一部分底层控制，换来了安全感、可移植性和 JS 友好的异步接口。

14.3 管线构建：隐式状态 vs 不可变对象

API管线怎么来特点
OpenGL编译 / 链接 shader 得到 program；绘制前绑定 VAO、纹理、混合、深度等状态管线是"当前全局状态的隐式组合"，改状态成本低，但容易状态泄漏、难缓存。
MetalMTLRenderPipelineDescriptor → MTLRenderPipelineState顶点格式、像素格式、深度状态在创建时固定；对象不可变，易缓存。
VulkanVkGraphicsPipelineCreateInfo 描述每个固定阶段最完整，也最冗长；必须与 VkRenderPass 子 pass 兼容；常配 pipeline cache。
WebGPUcreateRenderPipeline() / createComputePipeline()显式描述 vertex buffers、fragment targets、depthStencil；layout:'auto' 可自动推导绑定布局；创建即验证。

WebGPU 的管线形态：

TypeScript
const pipeline = device.createRenderPipeline({
    // 自动推导绑定布局
    layout: 'auto',
    vertex: {
        module: shader, // 着色器模块
        entryPoint: 'vs_main', // 顶点入口函数名
        // 顶点布局：位置 3 float + 颜色 3 float
        buffers: [{ arrayStride: 24, attributes: [
            { shaderLocation: 0, offset: 0,  format: 'float32x3' }, // 对应 @location(0)
            { shaderLocation: 1, offset: 12, format: 'float32x3' } // 对应 @location(1)
        ]}]
    },
    // 片段输出到画布格式
    // 片段输出到画布格式；fs_main 是片段入口
    fragment: { module: shader, entryPoint: 'fs_main', targets: [{ format }] },
    primitive: { topology: 'triangle-list' }, // 三角形拓扑
    // 深度测试：近处覆盖远处
    depthStencil: { format: 'depth24plus', depthCompare: 'less', depthWriteEnabled: true } // 深度格式 depth24plus
});
WebGPU 的管线对象创建后不可变。视口 / scissor、混合常量等少量状态可在 pass 中动态设置；大多数配置变化需要新建管线。这与 Metal / Vulkan 更像，而与 OpenGL 的"随时改全局状态"不同。

14.4 数据绑定：全局槽位 vs 显式绑定集

API顶点数据Uniform / 资源映射方式
OpenGLglBindBuffer + glVertexAttribPointer，VAO 记录布局glUniform* / 纹理单元全局槽位，靠"当前绑定什么"决定；状态错误常见。
Metalpipeline 的 vertex descriptor 描述布局setBuffer:offset:atIndex:、纹理 / sampler 按 index 绑定命令编码器显式设置；高级用法可用 argument buffer。
VulkanVkVertexInputBindingDescription 写入管线descriptor set layout + pool + set，push constants 用于小数据@binding 由应用手动组织，最灵活也最繁琐。
WebGPUvertex.buffers[].shaderLocation 对应 WGSL @locationbind group layout + bind group，对应 @group/@binding创建时验证类型 / usage；没有裸指针，binding 数量有限制。

WebGPU 的绑定三件套：

TypeScript
// 1) 布局：声明"第 0 个 binding 是 uniform buffer"
const layout = device.createBindGroupLayout({ entries: [{
    binding: 0, // 对应 WGSL @binding(0)
    visibility: GPUShaderStage.VERTEX, // 顶点阶段可见
    buffer: { type: 'uniform' } // 绑定为 uniform buffer
}]});

// 2) 绑定组：把真实 buffer 填进这个插槽
const bindGroup = device.createBindGroup({
    layout, // 使用上面定义的布局
    entries: [{ binding: 0, resource: { buffer: uniformBuffer } }] // 把真实 buffer 填入 0 号插槽
});

// 3) WGSL 侧按编号读取
// @group(0) @binding(0) var<uniform> uniforms: Uniforms;
关键差异：OpenGL 的绑定是"当前状态"，WebGPU / Vulkan / Metal 的绑定是"不可变对象 + 显式索引"。后者更啰嗦，但可验证、可缓存、可并行编码，错误也更早暴露。

14.5 异步与同步：隐式驱动 vs 显式原语 vs Promise

APICPU 提交CPU 等 GPUGPU 内部同步队列 / 多线程
OpenGL调用通常只是入队，驱动隐式批处理glFinish() / fence / sync object驱动隐式插入同步context 通常绑定单线程，跨线程困难
MetalcommitCommandBuffer 提交到队列completion handler / MTLSharedEventMTLFence / memory barrier多线程编码命令缓冲是常规做法
VulkanvkQueueSubmitfence / vkWaitForFencespipeline barrier / subpass dependency / semaphore多 queue family，多队列并行，全部手动
WebGPUqueue.submit() 同步入队，GPU 异步执行onSubmittedWorkDone() / mapAsync()pass 之间、dispatch 之间隐式排序单一 FIFO queue；Worker 可承担计算编码，但不暴露多队列

WebGPU 的异步边界：

TypeScript
const adapter = await navigator.gpu.requestAdapter();   // Promise：选择 GPU 适配器
const device  = await adapter.requestDevice();          // Promise：创建设备

// 提交是同步的"入队"，实际执行由 GPU 异步完成
device.queue.submit([encoder.finish()]); // 同步入队，GPU 异步执行

// 等待某段工作完成
await device.queue.onSubmittedWorkDone(); // CPU 等待 GPU 完成已提交的工作

// 回读：copyBufferToBuffer 到 staging buffer，再异步映射
await staging.mapAsync(GPUMapMode.READ); // 映射 staging buffer 供 CPU 读取
const result = new Float32Array(staging.getMappedRange()).slice(); // 复制出视图，unmap 后仍可用
取舍：WebGPU 没有 Vulkan 式的 semaphore / barrier，浏览器替你保证 pass 与 dispatch 的顺序和资源可见性。好处是安全、少写样板；代价是你无法表达复杂的多队列依赖，也拿不到极致控制。

14.6 多线程与命令编码

API命令编码模型多线程能力
OpenGL直接调用 GL 函数改变全局状态弱；context 通常只能在创建它的线程使用。
Metal每个线程创建 / 填充自己的 command buffer强；Apple 的示例和引擎普遍并行编码。
Vulkan每个线程记录自己的 command buffer，再提交到 queue最强；也是复杂度来源之一。
WebGPUGPUCommandEncoder 一次性编码，finish 后得到 command buffer适度；Worker 可做计算 / 预处理，但对象模型不支持 Vulkan 式多队列共享。

常见坑：WGSL 对类型很严格。写 1 是整数，写 1.0 才是浮点；循环下标常用 0u / 1u，矩阵乘法要用 vec4f(position, 1.0) 把 vec3f 升成 vec4f。

15.3 入口函数与注解

注解（以 @ 开头）告诉 WebGPU"这个函数是什么、数据从哪里来"。

注解作用常见位置
@vertex顶点着色器入口：每个顶点执行一次。函数前
@fragment片段着色器入口：每个像素 / 片元执行一次。函数前
@compute计算着色器入口：每个线程执行一次。函数前
@location(n)输入 / 输出编号，对应 JS 的 shaderLocation 或颜色附件位置。参数或返回类型前
@builtin(position)内置变量：顶点阶段必须输出裁剪空间坐标。结构体字段或返回类型前
@builtin(global_invocation_id)内置变量：compute 线程的全局编号。compute 函数参数前
@group(g) @binding(b)资源插槽编号，对应 JS 的 BindGroup。全局变量前
@workgroup_size(x,y,z)一个 workgroup 里有多少线程。compute 函数前
WGSL
@vertex
fn vs(@location(0) pos: vec3f) -> @builtin(position) vec4f {
    // @location(0) 对应顶点缓冲的 0 号属性
    return vec4f(pos, 1.0);
}

@fragment
fn fs() -> @location(0) vec4f {
    // @location(0) 对应画布的第 0 个颜色附件
    return vec4f(1.0, 0.0, 0.0, 1.0);
}

15.4 资源绑定：uniform 与 storage

WGSL 不能直接访问任意内存，必须把资源声明为全局变量，再由 JS 侧 BindGroup 填入真实 Buffer。

声明含义JS 侧对应
var<uniform>所有线程共享的只读小数据，如 MVP 矩阵。GPUBufferUsage.UNIFORM + writeBuffer()
var<storage, read>只读大块数据，如矩阵乘法的输入矩阵。GPUBufferUsage.STORAGE
var<storage, read_write>可读写的全局缓冲，如 compute 的输出矩阵。storage buffer，必要时再用 staging buffer 回读
WGSL
struct Uniforms { mvp: mat4x4f }; // 16 个 f32 = 64 字节
@group(0) @binding(0) var<uniform> uniforms: Uniforms;

@group(0) @binding(1) var<storage, read> data: array<f32>;
三处必须对齐：JS 的 @group(0) ↔ getBindGroupLayout(0)；WGSL 的 @binding(0) ↔ entries[0].binding；var<uniform> ↔ resource: { buffer }。详见 5.2 节。

15.5 控制流与常用函数

WGSL 的控制流与 TypeScript 类似，但整数 / 浮点类型不能混用。

WGSL
// 循环：下标用 u32
for (var i = 0u; i < 4u; i = i + 1u) {
    sum = sum + matrixA[row * 4u + i];
}

// 条件：浮点比较结果是 bool
if (sum > 0.0) {
    output = input / sum;
}

// 常用内建函数
let v = normalize(vec3f(1.0, 2.0, 3.0)); // 归一化
let s = max(0.0, dot(n, lightDir));       // 点积 + 截断
let c = mix(colorA, colorB, t);           // 线性插值
场景函数说明
数学abs、max、min、exp、sqrt逐元素数学运算。
向量normalize、dot、cross、length图形计算常用。
插值mix、smoothstep颜色 / 梯度插值。
选择select(a, b, cond)类似三元表达式：cond ? b : a。

15.6 常见坑清单

坑正确写法原因
1 与 1.0 混用浮点运算写 1.0，索引写 1uWGSL 不会自动做隐式类型转换。
顶点阶段忘了 @builtin(position)顶点函数必须输出裁剪空间坐标否则光栅化不知道顶点在哪里。
@location 对不上JS 的 shaderLocation 与 WGSL 一一对应编译可能通过，但画面错位或报错。
@binding 对不上与 BindGroup 的 binding 一致setBindGroup 时校验失败。
struct 布局与 JS 不一致用 Float32Array 按字段顺序写入，注意对齐Uniform / storage 是原始字节布局，没有反射魔法。
试图写 var<uniform>需要写就用 var<storage, read_write>uniform 在所有线程间共享，必须只读。
